# Splitting the database roles

The app and the migrations currently use the same PostgreSQL role, so the role that
serves traffic can also `DROP TABLE`. This splits them: one role that reads and
writes rows, one that can change the schema.

> Status: **script ready and verified locally (`prisma/roles.sql`), not yet applied
> to production.** Applying it changes `DATABASE_URL` in Vercel, so it is a
> deliberate cutover with a rollback you should read first — see §5.

## 1. The two roles

| Role | Used by | Privileges |
| --- | --- | --- |
| `kairos_app` (new) | `DATABASE_URL` — the running app | `SELECT`, `INSERT`, `UPDATE`, `DELETE` on tables; `USAGE` on sequences; **no** `CREATE`, `TRUNCATE`, `REFERENCES` or `TRIGGER` |
| owner (existing) | `DIRECT_URL` — `prisma migrate deploy` only | unchanged; owns the schema |

Prisma needs DDL only for migrations. The app never issues `CREATE`, `ALTER` or
`DROP`, which is why this is a drop-in change and not a rewrite.

## 2. Apply it

Set the password **separately** — it must never be written into a file that could be
committed:

```bash
# 1. the grants (idempotent: safe to re-run)
#    `bash -c` so $DIRECT_URL is expanded by the guard's environment, not yours.
scripts/with-prod-env.sh bash -c 'bunx prisma db execute --url "$DIRECT_URL" --file prisma/roles.sql'

# 2. the password, read from a prompt, never a literal in shell history
read -rs KAIROS_APP_DB_PASSWORD
printf "ALTER ROLE kairos_app PASSWORD '%s';" "$KAIROS_APP_DB_PASSWORD" \
  | scripts/with-prod-env.sh bash -c 'bunx prisma db execute --url "$DIRECT_URL" --stdin'
unset KAIROS_APP_DB_PASSWORD
```

`--url` is explicit on purpose: an inline `DATABASE_URL=…` loses to `.env` for the
Prisma CLI (see `docs/troubleshooting.md`), while `--url` cannot be overridden and
needs no temporary schema.

## 3. Cut the app over

In Vercel, for **Production** and **Preview**:

```
DATABASE_URL = postgresql://kairos_app:<password>@<pooled host>:5432/<db>?sslmode=require
DIRECT_URL   = <unchanged, the owner role>
```

Redeploy. Nothing else changes: the app already reads only `DATABASE_URL`, and
`DIRECT_URL` is used by the CLI alone.

## 4. Verify, do not assume

```sql
-- Expected: f | t | f | t
SELECT has_schema_privilege('kairos_app', 'public', 'CREATE'),
       has_table_privilege('kairos_app', '"Task"', 'SELECT'),
       has_table_privilege('kairos_app', '"Task"', 'TRUNCATE'),
       has_table_privilege('kairos_app', '"Task"', 'DELETE');
```

Then, from the app side:

```bash
curl -s https://<your-app>/api/health          # {"ok":true,"database":"ok"}
scripts/with-prod-env.sh bunx prisma migrate status   # still uses the owner role
```

The full suite was run against a local database as `kairos_app` and all **30**
integration tests passed, which is the real proof that the app needs no DDL.

## 5. Rollback

Point `DATABASE_URL` back at the owner role and redeploy. The role split grants
nothing that must be undone, so the two states are interchangeable; `kairos_app`
can be left in place (`DROP ROLE kairos_app` only after revoking its grants and
ensuring no session is connected).

## 6. Verified locally (2026-10-20)

| Check | Result |
| --- | --- |
| `prisma/roles.sql` applies cleanly, twice | ✅ idempotent |
| `has_schema_privilege('kairos_app','public','CREATE')` | `false` |
| `has_table_privilege('kairos_app','"Task"','SELECT' / 'TRUNCATE')` | `true` / `false` |
| `CREATE TABLE` as `kairos_app` | `ERROR: permission denied for schema public` |
| `TRUNCATE "Task"` as `kairos_app` | `ERROR: permission denied for table Task` |
| Integration suite as `kairos_app` | 30/30 pass |

## 7. Production caveat — verified, and it blocks the split

Prisma Postgres **refuses to create roles**:

```
$ scripts/with-prod-env.sh bash -c 'bunx prisma db execute --url "$DIRECT_URL" --file prisma/roles.sql'
Error: ERROR: restricted superuser cannot create roles
```

So the split cannot be applied to the current production database. Options, in
order of preference:

1. **Ask Prisma for a second role** (or a database where the project role may
   `CREATEROLE`). Then §2–§4 apply unchanged.
2. **Self-host the database** (Neon, RDS, a VM). `prisma/roles.sql` is written for
   plain PostgreSQL and already verified (see §6).
3. **Accept the risk with compensating controls** — the current state:

| Control | Status |
| --- | --- |
| Dynamic SQL in the app | **none**: no `$executeRawUnsafe`, `$queryRawUnsafe`, `Prisma.raw` anywhere in `src/` (grep is part of the review checklist) |
| All queries | generated by Prisma Client — parameterised by construction |
| Tenant filtering | `scopedPrisma` injects `userId` on every tenant model, verified against `schema.prisma` by a unit test |
| Migrations | only `prisma migrate deploy`, run deliberately; Vercel never migrates |
| Blast radius | the app role is also the *owner*, so a hypothetical injection could `DROP TABLE`; backups are exportable JSON, and Prisma Postgres keeps point-in-time recovery |

The residual risk is therefore "a bug that writes raw SQL", not "any injection".
Keep it that way: a future `$executeRawUnsafe` should be rejected in review, and
`scripts/check-boundaries.sh` (phase 8) can be extended to fail on it.

**One raw statement now exists on purpose** — the rate-limit counter
(`server/rate-limit.ts`) uses a single `Prisma.sql`-style tagged query with bound
parameters, because an atomic `ON CONFLICT … RETURNING` has no typed equivalent.
It interpolates values, never identifiers, and is the only one in `src/`.
